# 06 · 默契度测试（S 级）

> 2026-08-04 · 状态：设计完成，候选排期 · 形态：纯前端（答案编码进 URL，无后端）

## 1. 一句话

答 10 道关于你俩的题，生成专属链接发给对方；对方答完，出「默契度 73%」对比报告——链接必须被第二个人打开，结果才存在。

## 2. 传播机制（为什么是 S 级）

池子里唯一有**结构性传播优势**的点子：传播不依赖「用户愿不愿意转」，而是产品闭环强制发生——不发链接就没有结果。一次完整使用 = 至少一次定向拉新，且发送场景（聊天窗口）就是产品的使用场景。

- **情绪钩子**：关系好奇心（「我们到底多默契」）+ 对比谈资（73% vs 隔壁俩 91%）
- **转发动机**：发起即转发（机制内置）；出结果后对比卡二次传播
- **对标**：英文 couple quiz 类 App 验证过需求；中文网页轻量形态是空档

## 3. 用户流程

```
发起方：选题库（好友版/情侣版）→ 填昵称 → 答 10 题
      → 生成挑战链接 + 「挑战发起卡」→ 复制链接发给对方
应战方：打开链接（「XX 向你发起默契挑战」）→ 填昵称 → 答同 10 题
      → 本地比对 → 对比报告页 → 保存「默契度对比卡」发回给发起方
```

- 全程无注册无后端；应战方答完即刻出结果（发起方答案就在 URL 里）
- **闭环设计**：对比卡是「发回去」的社交动作载体——结果回流靠人和人之间本来就开着的聊天窗口，不需要服务器
- **兜底**（链接发出去没人理）：发起方答完立即得到「挑战发起卡」，含自己的答题风格锐评（「你是 78% 的人里最念旧的那种朋友」），单人也有可保存的产出

## 4. 题库设计

- v1 两套题库，走配置驱动（复用 [02](02-mental-state-check.md) 的「配置即产品」思路）：
  - **好友版**：「你们聚会谁负责找店」「TA 深夜 emo 会先干嘛」「你们最默契的时刻发生在哪」
  - **情侣版**：「谁先说的第一句喜欢」「吵架后谁先低头」「TA 最近一次让你心动是因为什么」
- 固定 10 题、每题 4 选项；**判定逻辑 = 双方选同一选项算默契**，所以题目必须是「答案客观存在、双方视角一致」的事实/习惯题，不能是主观偏好题（这是题目筛选的硬标准）
- 题目本身要好笑到值得截图（同 02 的「题目即内容」标准）

## 5. URL 编码规格（本站的核心技术设计）

```
链接形式：https://<域名>/c?d=<base64url(JSON)>
JSON：{ v: 1, q: "friend" | "couple", n: "发起方昵称(≤8字)", a: [0,2,1,3,...] }  // a 长度固定 10，值 0~3
```

- 直接 JSON → UTF-8 → base64url，不做位压缩：总长约 150 字符，可接受，且可调试
- `v` 版本号为未来题库改版留兼容口；解码后严格校验（版本/题库存在/答案数组长度与取值），**任何校验失败都落到首页并提示「链接失效了，重新发起一个吧」**，绝不白屏
- 昵称长度前端限制 8 字，编码前再截断一次（防手改 URL 撑爆卡片排版）
- 隐私：答案随挑战链接传递，应用不建立数据库保存挑战内容；由于 `?d=` 会随请求发送给托管基础设施，页面明确提醒只发给信任的人，统计脚本必须排除查询参数

## 6. 计分与报告

- 默契度 = 相同选项数 × 10%，映射五档称号：

| 分数 | 称号 |
|------|------|
| 90~100 | 灵魂共振 |
| 70~89 | 双向奔赴 |
| 50~69 | 还在磨合 |
| 30~49 | 各过各的 |
| 0~29 | 塑料情谊（好友版）/ 建议聊聊（情侣版） |

- 报告页含**逐题对比明细**：答一致的题打钩高亮（「第 3 题你们想到一起了」），不一致的题展示双方各选了什么——明细本身就是聊天素材，驱动结果回流
- 低分文案必须好笑不伤人（塑料情谊要能笑着发出去）；情侣版低分档文案单独打磨，避免真吵架

## 7. 分享卡片

- 走 `shared/share-card` 管线，两张卡：
  - **挑战发起卡**（兜底产出）：昵称 + 挑战宣言 + 站名
  - **默契对比卡**（核心传播物）：双方昵称 + 默契度大数字 + 称号 + 最有梗的一条逐题对比 + 站名
- 对比卡配色按档位变化（高分暖色/低分冷色），九宫格里可辨识

## 8. 埋点

标准三事件 + 本站闭环漏斗：

- `generate`：发起方生成链接
- `challenge_opened`：带 `d` 参数的访问（= 链接被打开）
- `challenge_completed`：应战方出结果
- **闭环率 = challenge_opened / generate**，是本站生死指标（预期 > 40%；低于说明链接在聊天场景传不动，机制假设不成立）

## 9. 测试

- 编解码 roundtrip 单测：中文/emoji 昵称、截断、坏 base64、篡改答案数组、未知版本号
- 计分与档位边界单测（0/29/30/49/50/69/70/89/90/100）
- 手工验收：微信内发起→复制链接→另一台手机微信内打开全流程；链接在微信/QQ/钉钉粘贴不被截断或转义

## 10. 风险

| 风险 | 应对 |
|------|------|
| 微信对带长参数外链敏感（拦截/提示） | 上线首日双机实测；被拦则准备短域名 + 参数进 hash（`#d=`）两个备选方案 |
| 应战方打开后流失（10 题太长） | 一屏一题点选即跳（同 02），实测完测时长压到 40 秒内；`q_answered` 埋点找流失题 |
| 题目不适配某些关系（塑料同事测情侣题） | v1 只上好友/情侣两套，题库入口明确分流 |
